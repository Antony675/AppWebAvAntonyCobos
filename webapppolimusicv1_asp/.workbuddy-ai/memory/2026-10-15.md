# 2026-10-15 — PoliMusic: desarrollo completo de la aplicación web

## Contexto
Proyecto de Aplicaciones Web Avanzadas (EPN, 8vo semestre). Se desarrolló desde cero
"PoliMusic", un clon funcional de Spotify en **ASP Clásico (VBScript)** + HTML5/CSS3/JS
vanilla, con SQL Server en contenedor (puerto 14333).

## Decisión de arquitectura
- Se optó por **ASP Clásico puro con ADODB**, sin frameworks ni dependencias externas
  (sin CDN). Toda la iconografía es SVG en línea generado desde VBScript.
- Capa de datos centralizada: `_includes/conexion.asp` (conexión + helpers) y
  `_includes/consultas.asp` (repositorio de SQL de lectura).
- Layout por fragmentos incluidos (`layout_superior.asp` / `layout_inferior.asp`) para
  evitar duplicación entre `dashboard.asp` y `admin/panel.asp`.
- La conexión usa `Provider=MSOLEDBSQL` con **fallback automático a `SQLOLEDB`** si el
  proveedor moderno no está instalado en el servidor.

## Hallazgos importantes sobre los datos
- El script `BDD_PoliMusic.sql` está codificado en **UTF-16 LE** (no UTF-8); hay que
  decodificarlo antes de leerlo.
- Las rutas en la BD usan formato `~/songFiles/x.mp3` (carpeta en camelCase) y a veces
  con **barras invertidas** (`~\playlistImages\Playlist2.png`). Se resolvió con la
  función `ResolverRecurso()`, que detecta la carpeta por nombre (case-insensitive) y
  normaliza separadores.
- Los usuarios semilla del script son `userNormal` y `userAdmin`, pero el requerimiento
  pedía `usersAdmin` y `AntonyCobos`. Se documentó que el script debe ajustarse a esos
  nombres (o que el login es case-insensitive a nivel de SQL Server).
- La BD referencia imágenes (`~/albumImages/album*.png`, `~/artistImages/artist*.jpg`)
  que **no existían** en `SongFilesAndImages_resources`. Se generaron 5 carátulas de
  álbum y 5 retratos de artista con Pillow, alineados a la paleta del dark mode.

## Incidencia del despliegue en IIS y su reparación

El usuario ejecutó `deploy-iis.cmd` con éxito (38 archivos publicados, app `/polimusic`
creada, pool `PoliMusicPool`, SQL Server accesible), pero al abrir
`http://localhost/polimusic/` obtuvo una página en blanco con
**"HTTP/1.1 Error en nueva aplicación"** (HTTP 501).

### Diagnóstico: tres defectos en la configuracion publicada

1. **HTTP 501 (la causa del fallo visible).** El `web.config` publicado declaraba
   `<asp enableParentPaths="false">`, pero todas las páginas usan
   `<!--#include file="..."-->` con rutas relativas de subida de nivel
   (`../_includes/...` en `admin/`, `_includes/...` en raíz). ASP no puede resolverlas
   con esa directiva en `false` y aborta la ejecución → 501. Además, el intento del
   script `Set-WebConfigurationProperty -Name "enableParentPaths"` fallaba porque la
   sección `<asp>` ya estaba fijada por el propio `web.config` (conflicto de sección
   bloqueada), de modo que el valor incorrecto permanecía publicado.
2. **`timeout="30"` inválido.** El elemento `<session>` de IIS exige el formato
   `[-][d.]hh:mm:ss[.ff]`; un entero provoca el error reportado por el script.
3. **`hiddenSegments` duplicados.** El script y el `web.config` declaraban ambos
   `_includes` / `_logs` → "entrada de colección duplicada con clave única 'segment'".

### Correcciones aplicadas

- `polimusic/web.config`: `enableParentPaths="false"` → `"true"` y
  `<session timeout="30">` → `"00:30:00"`.
- `polimusic/deploy-iis.ps1`:
  - `enableParentPaths` ahora se aplica en su propio `try/catch` (tolerante a fallo) y
    se **verifica el valor efectivo** con `Get-WebConfigurationProperty` al final.
  - Se desbloquea preventivamente la sección `<asp>` con
    `Set-WebConfiguration ... -Metadata "overrideModeDefault:Allow"`.
  - `defaultDocument`: `Clear-WebConfiguration` + reinserción idempotente de
    `login.asp` / `dashboard.asp` / `index.asp` (antes usaba `Set-... -Name "."`).
  - `hiddenSegments`: `Clear-WebConfiguration` antes de reinsertar, más los segmentos
    por defecto (`bin`, `App_Code`, `App_Data`, `web.config`).
- **Nuevos archivos:** `polimusic/reparar-iis.ps1` + `polimusic/reparar-iis.cmd`
  (Opción C del README). Reparación dirigida sin redespliegue completo: publica el
  `web.config` corregido, sincroniza `_includes`/`admin`/`css`/`js`, fuerza
  `enableParentPaths`, limpia segmentos ocultos, ajusta permisos NTFS, recicla el pool
  y prueba la respuesta clasificando el código HTTP (200/500/501) con guía de acción.
- `polimusic/README.md`: nueva sección "Solución de problemas conocidos" con tabla
  síntoma → causa → solución.

### Validaciones

- `deploy-iis.ps1` y `reparar-iis.ps1` parseados con el AST de PowerShell: **sin errores**.
- `reparar-iis.ps1` compatible con Windows PowerShell 5.1 (sin `&&`, `||`, `??`, `?.`).
- `web.config` parseado como XML: válido; `enableParentPaths=true`, `timeout=00:30:00`.

## Bug de bloqueo interactivo en los scripts (segunda iteración)

Al ejecutar `deploy-iis.cmd` con los arreglos anteriores, el despliegue avanzó
correctamente (40 archivos publicados, app `/polimusic` recreada, pool reutilizado)
pero **se detuvo pidiendo entrada** en la fase de ASP:

```
cmdlet Set-WebConfiguration en la posición 1 de la canalización de comandos
Proporcione valores para los parámetros siguientes:
Value:
```

### Causa

Se había añadido una llamada inventada para desbloquear la sección:

```powershell
Set-WebConfiguration -PSPath "MACHINE/WEBROOT/APPHOST" -Filter "system.webServer/asp" `
    -Metadata "overrideModeDefault:Allow"
```

`Set-WebConfiguration` **no acepta** el parámetro `-Metadata`; PowerShell resolvió los
argumentos como posicionales, no encontró un valor y entró en **modo interactivo**
solicitando `Value:`. Eso congela el script en una ventana elevada (peor de lo que
parece: el usuario no puede continuar).

### Corrección

- Se **eliminó por completo** la llamada a `Set-WebConfiguration -Metadata` en
  `deploy-iis.ps1` y en `reparar-iis.ps1`, sustituyéndola por un comentario de diseño
  que explica por qué no se usa.
- Se limpió un bloque `try/catch` huérfano que había quedado duplicado en
  `deploy-iis.ps1` (un `Escribir-Aviso` suelto dentro de un `try` vacío).
- Estrategia vigente: el `web.config` declara las directivas y las llamadas a
  `Set-WebConfigurationProperty` se ejecutan con tolerancia a fallo; el valor efectivo
  se verifica con `Get-WebConfigurationProperty` al final.

### Nuevo script de verificación

Se añadió `polimusic/verificar-iis.ps1` + `polimusic/verificar-iis.cmd` (Opción D del
README). **No vuelve a publicar**: comprueba archivos presentes, contenido del
`web.config` publicado, registro de la app y del pool, aplica las directivas ASP
faltantes, ajusta permisos NTFS, recicla el pool y prueba la URL. Clasifica la respuesta
con guía concreta: 200 (funciona), 500 (error de script → abrir en navegador),
501 (ejecutar `reparar-iis.cmd`), 0 (revisar `W3SVC`). Además prueba el puerto 14333.

### Validaciones

Los **tres** scripts (`deploy-iis.ps1`, `reparar-iis.ps1`, `verificar-iis.ps1`) pasan el
parser AST de PowerShell sin errores, contienen **0** llamadas a `Set-WebConfiguration`
sin `-Property`, y no usan operadores exclusivos de PS7 (`&&`, `||`, `??`, `?.`).

### Lección aprendida

No inventar cmdlets ni parámetros de la API de IIS. `Set-WebConfiguration` no tiene
`-Metadata`; para el modo de sobrescritura se usa
`Set-WebConfigurationProperty -PSPath MACHINE/WEBROOT/APPHOST ... -Name . -Value ...` o
`appcmd set config /section:... /overrideModeDefault:Allow`. Cualquier cmdlet mal
formado en un script elevado provoca un bloqueo interactivo difícil de detectar.

## Causa raíz definitiva del HTTP 501 (tercera iteración) — RESUELTO

Tras ejecutar `reparar-iis.cmd`, el script reportó el mensaje decisivo:

```
Error: Esta seccion de configuracion no puede utilizarse en esta ruta. Esto sucede
cuando la seccion se bloquea en un nivel principal. El bloqueo se aplica de forma
predeterminada (overrideModeDefault="Deny") o se establece explicitamente mediante
una etiqueta de ubicacion con overrideMode="Deny" o el valor heredado
allowOverride="false".
Numero de linea: 35
Archivo: \\?\C:\inetpub\wwwroot\polimusic\web.config
```

### Diagnóstico correcto (el anterior era incompleto)

**La sección `<system.webServer/asp>` está BLOQUEADA a nivel de servidor**
(`overrideModeDefault="Deny"`). El `web.config` de la aplicación la declaraba en la
línea 35:

```xml
<asp scriptErrorSentToBrowser="true" enableParentPaths="true" codePage="65001">
```

Cuando un `web.config` intenta declarar una sección **bloqueada**, IIS **rechaza el
archivo completo** y responde **HTTP 501 a TODAS las peticiones** — no solo a las que
usan ASP. Es un efecto dominó: un atributo en una sección no sobrescribible invalida
toda la configuración de la aplicación.

Por eso los intentos previos (`enableParentPaths=true` en el archivo, reciclar el pool,
permisos) no servían: el `web.config` era el problema, no la solución.

También se confirmó que el error `'bin'` de `hiddenSegments` venía de manipular la
colección **en paralelo** al `web.config` (doble fuente de verdad).

### Solución definitiva

1. **`polimusic/web.config` — se ELIMINÓ por completo la sección `<asp>`.** Toda la
   configuración de ASP se aplica ahora a nivel de servidor/aplicación con `appcmd`.
   Se añadió un comentario extenso explicando el porqué.
   También se corrigió `<hiddenSegments>`: se quitaron los `<remove segment="_includes">`
   / `<remove segment="_logs">`, porque `_includes` y `_logs` **no existen por defecto en
   IIS** y un `<remove>` de una entrada inexistente provoca error de configuración.
   Ahora solo hay `<add>`.
2. **Los tres scripts usan `appcmd.exe`** (herramienta correcta, sí funciona elevada) en
   lugar de cmdlets frágiles:
   ```
   appcmd set config /section:system.webServer/asp /overrideModeDefault:Allow /commit:apphost
   appcmd set config "Default Web Site/polimusic" /section:system.webServer/asp /enableParentPaths:"true"
   appcmd set config ... /section:system.webServer/asp/session /timeout:"00:30:00"
   ```
   Se desbloquean `system.webServer/asp`, `.../asp/session` y `.../asp/limits`.
3. **Se eliminó la manipulación programática de `hiddenSegments` y `defaultDocument`**
   de los scripts: el `web.config` es la **única fuente de verdad** para esas secciones,
   lo que elimina de raíz los errores de "entrada duplicada".
4. `reparar-iis.ps1` conserva el flujo completo: desbloquear → publicar web.config sin
   `<asp>` → aplicar directivas con appcmd → verificar `enableParentPaths="true"` →
   permisos → reciclar pool → probar URL con clasificación 200/500/501.

### Validaciones

Los tres scripts pasan el parser AST de PowerShell sin errores, con **0** llamadas a
`Set-WebConfiguration` mal formadas, **0** manipulación de `hiddenSegments` por cmd, y
sin operadores de PS7. El `web.config` es XML válido, **no declara `<asp>`**, y sus
`hiddenSegments` son `_includes, _logs`.

### Regla de oro para IIS + ASP Clásico (aplicar en futuros proyectos)

- La sección `<asp>` casi siempre está bloqueada por defecto. **Nunca declararla en un
  `web.config` de aplicación**: configura `enableParentPaths`, `codePage` y `session`
  con `appcmd ... /commit:apphost` desde el script de despliegue.
- Un `web.config` que declara una sección bloqueada **invalida la app entera** (501).
- No duplicar colecciones (`hiddenSegments`, `defaultDocument/files`) entre el
  `web.config` y los cmdlets: una sola fuente de verdad.
- `<remove>` solo para entradas que existen por defecto; las propias van con `<add>`.

## Cuarta iteración: de 501 a 500 y solución definitiva con #include virtual

Tras la tercera iteración el síntoma cambió: **de 501 a 500**. Eso confirmó que el
bloqueo del `<asp>` en el `web.config` quedó resuelto (ASP ya ejecuta). El 500 era un
error de script, pero con dos subproblemas nuevos visibles en la salida:

1. `ERROR: Atributo 'overrideModeDefault' desconocido` — **`appcmd set config` no acepta
   `/overrideModeDefault`**. Ese nombre es del atributo XML de applicationHost.config,
   no un parámetro CLI. Sintaxis correcta:
   ```
   appcmd unlock config /section:system.webServer/asp
   appcmd set config /section:system.webServer/asp /overrideMode:Allow /commit:apphost
   ```
2. `enableParentPaths NO quedo en true` + `locked="true"` en la config de la app → la
   sección sigue bloqueada y la directiva no se puede aplicar por herencia.

### Solución definitiva (dos frentes)

**A. Eliminar la dependencia de `enableParentPaths` — la clave real.**
Se convirtieron **los 24 `#include file=` a `#include virtual=`** en los 5 archivos ASP:

| Archivo | Includes |
|---------|----------|
| `login.asp` | 3 |
| `logout.asp` | 3 |
| `dashboard.asp` | 7 |
| `admin/panel.asp` | 7 |
| `admin/procesar.asp` | 4 |

`#include virtual` resuelve desde la raíz de la aplicación y **no requiere
`enableParentPaths`**. Con esto la app funciona aunque la sección siga bloqueada.
Rutas usadas: `/polimusic/_includes/<archivo>.asp`.

**B. Corregir la sintaxis de appcmd** en los tres scripts (`unlock config` +
`/overrideMode:Allow`), y `enableParentPaths` pasa a ser **opcional** (solo
compatibilidad), no un requisito.

**C. `_includes` fuera de `hiddenSegments`.** Ocultar el segmento podía interferir con
la resolución en algunas configuraciones. La protección real la da que los fragmentos
son `.asp` (se ejecutan, nunca se descargan como texto). Solo queda `_logs` oculto.

### Validaciones

Los tres scripts pasan el parser AST sin errores, **0** ocurrencias de
`overrideModeDefault` en código (solo en comentarios explicativos), sin operadores PS7.
El `web.config` es XML válido, no declara `<asp>` y su `hiddenSegments` es `_logs`.

### Estado

Pendiente que el usuario vuelva a ejecutar `reparar-iis.cmd`, que ahora publica los .asp
con `#include virtual` y aplica el desbloqueo con la sintaxis correcta.

## Quinta iteración: el error real era global.asa (ASP 0116)

Con `scriptErrorSentToBrowser="true"` ya activo, el navegador mostró por fin el error
concreto:

```
Páginas Active Server error 'ASP 0116'
Falta delimitador de cierre de script
/LM/W3SVC/1/ROOT/POLIMUSIC/global.asa, línea 1
El bloque Script no contiene la etiqueta de cierre del script (%>).
```

### Causa raíz

El `global.asa` estaba **envuelto en un bloque `<% ... %>`**:

```
<%
' comentario...
<script language="VBScript" runat="Server">
...
</script>
```

**Un `global.asa` NUNCA debe envolverse en `<% %>`.** El archivo debe contener
exclusivamente bloques `<script language="VBScript" runat="Server"> ... </script>`.
Al abrir `<%` en la línea 1, el parser de ASP intenta consumir todo el archivo como
código VBScript y, al encontrarse con `<script ...>` (texto literal, no código), no halla
el `%>` de cierre → **ASP 0116**.

Y como ASP compila `global.asa` **antes que cualquier página**, ese error tumba TODA la
aplicación con HTTP 500, independientemente del contenido de `login.asp`.

### Correcciones aplicadas

1. **`polimusic/global.asa` reescrito sin el `<% %>` envolvente.** Ahora empieza
   directamente con el bloque `<script language="VBScript" runat="Server">` y cierra con
   `</script>`. Se documentó el formato correcto en el encabezado del archivo.
2. **`unlock config` solo con secciones válidas.** Se eliminaron
   `system.webServer/asp/session` y `/limits` de las llamadas a `appcmd unlock config`:
   **no son secciones de configuración** (son sub-elementos) y appcmd devolvía
   "Sección de configuración desconocida". Solo `system.webServer/asp` es válido para
   `unlock`. Para `set config` sí se acepta `/section:system.webServer/asp/session`.
3. **Reinicio completo del sitio en `reparar-iis.ps1`.** `global.asa` solo se lee al
   **arrancar la aplicación**; reciclar el pool no siempre basta. Ahora el script hace
   `Stop-Website` + `Start-Website` antes de reciclar, garantizando la relectura.
4. **Verificación automática de la estructura de `global.asa`** en el script: detecta si
   la primera línea abre `<%` y avisa con `Fallo` si es así.
5. **Usuarios corregidos:** el usuario confirmó que son **`userAdmin`** (sin la "s") y
   **`AntonyCobos`**. Se reemplazó `usersAdmin` → `userAdmin` en `login.asp`, `README.md`
   y los tres scripts de despliegue.

### Validaciones

Los tres scripts pasan el parser AST sin errores. Los 6 archivos ASP tienen delimitadores
`<% %>` balanceados (login 9/9, logout 2/2, dashboard 139/139, global.asa 2/2,
panel 162/162, procesar 2/2). El `global.asa` empieza correctamente con un comentario,
tiene `<script language="VBScript" runat="Server">` y su `</script>`.

### Regla de oro añadida

**`global.asa` no lleva `<% %>` envolvente.** Solo bloques `<script runat="Server">`.
Un error ahí tumba toda la aplicación con 500 antes de ejecutar cualquier página.

## Sexta iteración: ASP 0137 (el `'` comentario contenía `<%`)

Tras corregir el envolvente, el error evolucionó de `ASP 0116` a **`ASP 0137`**:

```
Páginas Active Server error 'ASP 0137'
Bloque Script global no válido
/LM/W3SVC/1/ROOT/POLIMUSIC/global.asa, línea 8
Cada bloque Script debe ser uno de los procedimientos Global.asa autorizados. Las
directivas Script con <% %> no están autorizadas dentro del archivo Global.asa. Los
nombres de procedimientos autorizados son Application_OnStart, Application_OnEnd,
Session_OnStart o Session_OnEnd.
```

### Causa raíz (muy sutil)

El encabezado decorativo que puse al arreglar el error anterior contenía, **dentro de un
comentario VBScript `'`**, el texto literal:

```vb
'   Un global.asa NO debe envolverse en un bloque <% ... %>. El archivo contiene
```

El parser de `global.asa` **detecta el literal `<%` aunque esté dentro de un comentario**
y lo interpreta como una directiva Script, lo que dispara ASP 0137. Es decir: la propia
documentación del arreglo reintrodujo el error en otra forma.

### Corrección definitiva

`global.asa` reducido a su **forma canónica mínima**:

```vbscript
<script language="VBScript" runat="Server">
Sub Application_OnStart() ... End Sub
Sub Session_OnStart() ... End Sub
Sub Session_OnEnd() End Sub
Sub Application_OnEnd() End Sub
</script>
```

Sin encabezado, sin comentarios decorativos, sin `<%` en ningún sitio, sin BOM. Verificado:
primeros bytes `60,115,99` (`<sc`), `0` ocurrencias de `<%`/`%>`, empieza directamente con
`<script>`.

### Mejoras en el script de reparación

- La verificación de `global.asa` ahora **busca `<%` o `%>` en TODO el archivo** (no solo
  la primera línea) y exige que la primera línea no vacía sea `<script ...>`.
- Se añadió `Stop-Website` + `Start-Website` + reciclaje del pool + **`iisreset /restart`
  como respaldo** si la app no responde 200 tras el reinicio normal. `global.asa` solo se
  relee al arrancar la aplicación, y la caché de plantillas ASP puede servir la versión

## Séptima iteración: `Name redefined` por `Dim` duplicado entre include y página

### Error restante

Tras resolver `global.asa` y el `800a0400` de `Option Explicit`, la aplicación seguía
devolviendo **HTTP 500** en `dashboard.asp` y `admin/panel.asp`, pero respondía bien en
`login.asp`. El síntoma (500 solo en las páginas que usan el layout) fue la pista.

### Causa raíz (un clásico de ASP Clásico)

`#include virtual` **inserta el archivo en el mismo ámbito de script que la página**.
`_includes/layout_superior.asp` declara:

```vb
Dim strBase, strTituloDoc, strAvatar, strInicialesUsuario
strBase = URL_BASE
```

y las páginas que lo incluyen volvían a declarar:

```vb
Dim strBase          ' <-- dashboard.asp:32 y admin/panel.asp:33
strBase = URL_BASE
```

En VBScript, **un `Dim` duplicado en el mismo ámbito es un error FATAL de compilación**
(`Name redefined`). No es un error de ejecución: la página entera se rechaza y ASP
responde 500 sin siquiera entrar al script. `login.asp` no usa el layout, por eso
funcionaba.

### Corrección

En `dashboard.asp` y `admin/panel.asp` se sustituyó la redeclaración por una asignación
condicional:

```vb
' strBase ya viene declarada por layout_superior.asp (incluido arriba).
' Redeclararla seria 'Name redefined'.
If strBase = "" Then strBase = URL_BASE
```

### Lección general (regla de oro nº 5)

Un `#include` **comparte el ámbito** con la página anfitriona. Nunca redeclares con `Dim`
una variable que declare un include. Si un include ya la declara, en la página solo se
**asigna**. Aplica igualmente a los propios includes entre sí (`config.asp` declara
`URL_BASE`; ningún otro archivo debe redeclararla).

### `validar_asp.py` ampliado (séptima iteración)

El validador estático ahora simula el **orden real de ensamblado** de cada página
(`COMPOSICION_PAGINAS`) y detecta `Dim` duplicados en el ámbito global. Se añadió además:

- `codigo_vb_plano()`: extrae **solo** las regiones `<% ... %>`, neutralizando el HTML,
  y **excluye `<script>` de cliente (JavaScript) y `<style>`**. Esto eliminó los tres
  falsos positivos que quedaban:
  - `layout_superior.asp` — `If nSide = 0 Then` cerrado por `<% End If %>` en otro bloque.
  - `admin/panel.asp` — `For i = 0 To 4` … `<% Next %>` (el `Next` no está al inicio de
    línea porque comparte línea con `<%`).
  - `login.asp` — `for (var i = 0; i < botones.length; i++)` es **JavaScript de cliente**.

Resultado final: **13 archivos, 0 problemas**, y `[OK] Sin 'Dim' duplicados en el ambito
global de las paginas ensambladas.`

### Integración en los scripts de despliegue

- `reparar-iis.ps1`: nuevo paso **0.b** que ejecuta `validar_asp.py` **antes de publicar**
  y **cancela el despliegue** (con opción de forzar) si hay errores. Localiza Python en
  `~\.workbuddy-ai\binaries\python\versions\*` o en el PATH.
- `verificar-iis.ps1`: nuevo paso **0** que valida el código fuente y marca en rojo los
  errores de compilación — la causa más probable del 500.

### Estado

Código validado estáticamente sin errores. Los tres scripts PowerShell (`reparar-iis.ps1`,
`deploy-iis.ps1`, `verificar-iis.ps1`) pasan el parser AST sin errores. Pendiente de

## Octava iteración: `800a01b6 El objeto no acepta esta propiedad o método: 'EOF'`

### Progreso clave

Tras corregir el `Dim` duplicado, el **HTTP 500 de compilación desapareció**: la página
ya **renderiza** (se veía la barra lateral, el menú y el reproductor). Ahora el error es
de **tiempo de ejecución**:

```
Error de Microsoft VBScript en tiempo de ejecución '800a01b6'
El objeto no acepta esta propiedad o método: 'EOF'
/polimusic/_includes/layout_superior.asp, línea 90
```

### Causa raíz

`ListarPlaylists()` devolvía un Recordset **cerrado o inválido**, y `layout_superior.asp`
solo comprobaba:

```vb
If IsObject(rsSidePL) Then
    If Not rsSidePL Is Nothing Then   ' <-- NO basta
        Do While Not rsSidePL.EOF     ' <-- 800a01b6 si está cerrado
```

Un `Recordset` puede ser un objeto **no-Nothing pero cerrado** (si `rs.Open` falló y luego
`Set rs.ActiveConnection = Nothing` dejó el objeto en estado cerrado). Sobre un Recordset
cerrado, `.EOF` lanza `800a01b6`.

### Correcciones aplicadas

1. **`EjecutarConsulta()` (conexion.asp)** — reescrita para **garantizar** que devuelve
   un Recordset **ABIERTO** o `Nothing`, nunca uno cerrado:
   - Comprueba `Err.Number` tras `CreateObject`, tras `rs.Open` y tras liberar la conexión.
   - Verifica `rs.State <> 0` (adStateOpen) con `On Error Resume Next` antes de devolverlo.
   - Si el estado no es abierto → `rs.Close`, `Set rs = Nothing`.

2. **Nueva función `RsValido(ByRef rs)` (conexion.asp)** — la **única** guarda segura:
   ```vb
   Function RsValido(ByRef rs)
       Dim est
       RsValido = False
       On Error Resume Next
       If IsObject(rs) Then
           If Not rs Is Nothing Then
               est = rs.State
               If Err.Number = 0 And est <> 0 Then RsValido = True
           End If
       End If
       Err.Clear
       On Error GoTo 0
   End Function
   ```

3. **Sustitución sistemática** de `If IsObject(x) Then` / `If Not x Is Nothing Then` por
   `If RsValido(x) Then` en: `layout_superior.asp`, `dashboard.asp` (9 bloques),
   `admin/panel.asp` (7), `login.asp`, `_includes/conexion.asp` (`EjecutarEscalar`).

4. **`login.asp`**: se copian los campos del usuario a variables locales **antes** de
   `rs.Close`, porque `IniciarSesionUsuario` se llamaba con `rs(...)` tras cerrar el
   Recordset (orden frágil).

### Lección aprendida sobre la cirugía con regex (importante)

Los dos primeros intentos de sustitución automática **rompieron el conteo de `End If`**
(al fusionar dos `If` en uno hay que eliminar exactamente un `End If`). Provocaron
desbalances de -9 y -7. **La solución robusta fue el reemplazo IN-PLACE de la condición**
(`If IsObject(x) Then` → `If RsValido(x) Then`, misma cantidad de bloques) en lugar de
fusionar bloques. Regla: **nunca cambies el número de bloques al automatizar; solo cambia
la condición.**

### Verificación de simetría

Auditoría por variable: en `dashboard.asp`, `admin/panel.asp` y `layout_superior.asp`,
**cada** Recordset tiene exactamente `RsValido=1`, `Set = Nothing=1`, `Do While Not .EOF=1`,
y el balance `If/End If` es **0** en todos los archivos.

### `validar_asp.py` (octava iteración)

Añadida `validar_guardas_recordset()`: detecta variables usadas con `.EOF` o `rsX("campo")`
que **no** aparecen en ninguna llamada `RsValido(...)`. Salida final:

```
13 archivos analizados, SIN problemas detectados.
[OK] Sin 'Dim' duplicados en el ambito global de las paginas ensambladas.
[OK] Todos los Recordset estan protegidos con RsValido().
```

### Estado

Validación estática limpia. Pendiente: el usuario debe sincronizar los archivos

## Novena iteración: `800a000d No coinciden los tipos: 'rnd'`

### Progreso

El error `800a01b6` de Recordset quedó resuelto y **el login ya procesa la
autenticación**: ahora el fallo ocurre en el último paso, justo antes del redirect.

```
Error de Microsoft VBScript en tiempo de ejecución '800a000d'
No coinciden los tipos: 'rnd'
/polimusic/_includes/sesion.asp, línea 105
```

### Causa raíz (clásico de VBScript: ensombrecimiento de funciones)

En `GenerarToken()`:

```vb
Dim semilla, i, buf, c, rnd      ' <-- 'rnd' es el nombre de la funcion Rnd()
...
rnd = Int(Rnd() * Len(semilla)) + 1    ' <-- 800a000d
```

Al declarar `Dim rnd`, esa variable **ensombrece la función incorporada `Rnd()`**.
La expresión `Rnd()` deja de invocar la función y pasa a leerse como la variable
vacía → `Int(Empty * n)` → `800a000d "No coinciden los tipos: 'rnd'"`.

### Correcciones aplicadas

1. **`sesion.asp` → `GenerarToken()`**: `rnd` renombrado a `indice`; se eliminó
   también la variable `c`, que no se usaba. Añadido comentario explicativo.
2. **`conexion.asp` → `Sha1Hex()`** — el mismo bug **latente** en dos sitios:
   - `Dim asc` ensombrecía `Asc()`.
   - `Dim hex` ensombrecía `Hex(...)` (usado en `b = Hex(AscB(...))`).
   Renombrados a `oAsc`, `oEnc`, `oHash`, `oTextoHex`, `oByteHex`. Este código no se
   ejecutaba en el login con contraseñas en texto plano, pero **habría explotado**
   con credenciales SHA1.

### Escaneo sistemático realizado

Se auditó todo el proyecto (`**/*.asp` + `global.asa`) buscando identificadores que
colisionen con ~90 funciones/constantes de VBScript, en tres categorías:
- declaraciones `Dim`,
- **parámetros** de `Sub`/`Function` (`ByVal len` rompería igual),
- **contadores** de `For`.

Resultado tras las correcciones: **0 colisiones** en las tres categorías.
También se verificó `admin/procesar.asp`: 33 `Dim`, sin duplicados.

### `validar_asp.py` (novena iteración)

Añadida `validar_sombreado_funciones()` con el conjunto `RESERVADAS_VBSCRIPT`
(`rnd`, `hex`, `asc`, `len`, `date`, `timer`, `mid`, `left`, `right`, `replace`,
`split`, `int`, `cstr`…). Salida final:

```
13 archivos analizados, SIN problemas detectados.
[OK] Sin 'Dim' duplicados en el ambito global de las paginas ensambladas.
[OK] Todos los Recordset estan protegidos con RsValido().
[OK] Ningun identificador ensombrece funciones incorporadas de VBScript.
```
